* strategic-backup
:PROPERTIES:
:CUSTOM_ID: strategic-backup
:END:
strategic-backup automates nightly ZFS snapshot backups from an OmniOS
host to Backblaze B2, plus weekly automated restore tests that actually
verify a backup can be recovered — not just that an upload succeeded.

Pipeline: ~zfs snapshot~ → per-file SHA-256 checksums → ~zfs send -w~
piped through ~gzip~ and, unless the source dataset is already
ZFS-encrypted, ~openssl enc~ → uploaded to B2 via ~rclone~ → remote
retention enforced → an EDN manifest written locally and optionally
persisted to PostgreSQL/CockroachDB (a convenience index only — the tool
is fully operational without a database).

Only OmniOS-native tooling is used: ~zfs~, ~openssl~, ~gzip~, ~rclone~,
and POSIX shell. No Linux-specific commands.

** Installation
:PROPERTIES:
:CUSTOM_ID: installation
:END:
Requires a JDK and [[https://leiningen.org/][Leiningen]]. Build a standalone uberjar:

#+begin_example
$ lein uberjar
Created target/uberjar/strategic-backup-0.1.0-SNAPSHOT.jar
Created target/uberjar/strategic-backup.jar
#+end_example

~strategic-backup.jar~ is the one to deploy — it bundles every dependency
(Clojure, next.jdbc, timbre, clj-infisical, etc.). Its filename is fixed
(~:uberjar-name~ in =project.clj=, not the default
~<name>-<version>-standalone.jar~) precisely so it stays the same across
version bumps — cron entries, wrapper scripts, and deploy tooling never
need to change or glob for it. Copy it to wherever it'll run, e.g.
~/opt/strategic-backup/strategic-backup.jar~, overwriting the previous
version in place on each deploy.

** Configuration
:PROPERTIES:
:CUSTOM_ID: configuration
:END:
Configuration is an EDN file. Its path comes from the
~STRATEGIC_BACKUP_CONFIG~ environment variable, defaulting to
~/etc/strategic-backup/config.edn~.

#+begin_example
{:dataset                  "tank/syncthing"
 :test-dataset             "tank/restore-test"
 :staging-dir              "/var/backup/staging"
 :b2-bucket                "my-b2-bucket"
 :b2-path-prefix           "zfs-backups/"
 :retention-count          7
 :local-manifest-retention 14
 :compression              "gzip"
 :encryption-cipher        "aes-256-cbc"
 :snapshot-prefix          "backup"}
#+end_example

All keys above are required — a missing or unparseable config file, or a
config missing any of these keys, aborts the run with every missing key
logged at once.

*** Secrets
:PROPERTIES:
:CUSTOM_ID: secrets
:END:
Secrets are never stored in the config file. By default they're read
from environment variables:

| Variable                     | Required? | Purpose                                              |
|-------------------------------+-----------+-------------------------------------------------------|
| ~BACKUP_ENCRYPTION_KEY~       | No\*      | ~openssl enc~ passphrase (via ~-pass env:~, never argv) |
| ~RCLONE_CONFIG~               | No\*\*    | Path to an rclone config file with a B2 remote        |
| ~PGCONNSTRING~                | No        | Postgres/CockroachDB connection string (JDBC-style)   |
| ~ZFS_ENCRYPTION_PASSPHRASE~   | No\*      | Passphrase to ~zfs load-key~ a ZFS-encrypted ~:test-dataset~ during ~restore-test~ |

None of these are checked at startup, or by every subcommand — each is only
required by the specific subcommand(s) that actually touch it, and only
checked right before it's used there. Missing one you genuinely need still
aborts loudly, just later and more specifically, rather than crashing every
subcommand indiscriminately: e.g. ~--db-test~ never touches B2 at all, so a
missing ~RCLONE_CONFIG~ doesn't affect it; only ~backup~ and ~restore-test~
(which both need to reach B2) check for it.

\* ~BACKUP_ENCRYPTION_KEY~ and ~ZFS_ENCRYPTION_PASSPHRASE~ are mirror images of
each other, and between the two of them exactly one is actually needed for
any given dataset (see the table in [[#zfs-encryption-passphrase][ZFS encryption passphrase]] below).

\*\* Not needed at all if using Infisical mode with B2_KEY_ID/B2_APPLICATION_KEY
stored there instead — see [[#optional-infisical][Infisical for database and B2 credentials]] below.
Otherwise required by ~backup~ and ~restore-test~ (both reach B2); not
required by ~--db-test~ or ~--b2-test~ itself (a missing/bad B2 credential
there is exactly what ~--b2-test~ is meant to report, via ~{:ok false ...}~,
not a startup crash).

**** PGCONNSTRING format
:PROPERTIES:
:CUSTOM_ID: pgconnstring-format
:END:
~PGCONNSTRING~ is handed directly to ~next.jdbc/get-datasource~, so it must
be a full JDBC URL, not just a bare connection string. Works identically
whether the target is PostgreSQL or CockroachDB — both speak the same
wire protocol and use the same ~org.postgresql~ JDBC driver:

#+begin_example
jdbc:postgresql://myuser:mypassword@localhost:26257/backups?sslmode=verify-full&sslrootcert=/etc/strategic-backup/ca.crt
#+end_example

| Piece         | Example                    | Notes                                                        |
|----------------+-----------------------------+----------------------------------------------------------------|
| scheme         | ~jdbc:postgresql://~       | Required — this goes to ~DriverManager~, which needs the ~jdbc:~ prefix |
| user:password  | ~myuser:mypassword@~       | URL-encode either if they contain ~@ : / ? &~ (e.g. a literal ~@~ becomes ~%40~) |
| host:port      | ~localhost:26257~          | CockroachDB defaults to ~26257~; PostgreSQL defaults to ~5432~ |
| /dbname        | ~/backups~                 | Must match the database you create the table in below         |
| ?params        | ~sslmode=...&sslrootcert=...~ | Optional. CockroachDB requires TLS by default (secure mode) — omit both for a local ~--insecure~ cluster, or plain non-TLS PostgreSQL |

This is entirely optional — see [[#database-setup][Database setup]] below for what it's
for, and omit ~PGCONNSTRING~ entirely (or its Infisical equivalent) if you
don't want manifest persistence at all.

**** ZFS encryption passphrase (restore-test only)
:PROPERTIES:
:CUSTOM_ID: zfs-encryption-passphrase
:END:
If ~:dataset~ already has native ZFS encryption enabled (~zfs get
encryption <dataset>~ reports anything other than ~off~), backups skip
the ~openssl~ encryption stage entirely — the raw ~zfs send -w~ stream is
already encrypted, so there's no double encryption. That's transparent
for ~backup~, but ~restore-test~ has to unlock the *received* test
dataset before it can read files back off it to verify their checksums.
If the source dataset's ~keylocation~ is ~prompt~ (the normal case for an
interactively-entered passphrase), there's nothing to prompt in an
unattended cron job — that's what this secret is for.

~BACKUP_ENCRYPTION_KEY~ and ~ZFS_ENCRYPTION_PASSPHRASE~ are two sides of the
same coin — for any one dataset, exactly one of them actually does
anything:

| ~:dataset~ encryption | Backup archive protected by | Secret ~restore-test~ needs |
|-------------------------+-------------------------------+--------------------------------|
| ZFS-encrypted           | ZFS itself (native)          | ~ZFS_ENCRYPTION_PASSPHRASE~    |
| Not ZFS-encrypted       | ~openssl~ via ~BACKUP_ENCRYPTION_KEY~ | none (nothing to unlock) |

Neither secret is required at startup, since which one (if either) is
actually needed depends on ~:dataset~'s live encryption status, which isn't
known until the pipeline runs. Each is instead checked right at the point
it would be used, and aborts loudly if missing rather than failing with a
confusing shell error or silently skipping a step: ~backup~ checks before
touching the network if it's about to ~openssl~-encrypt; ~restore-test~
checks before ~zfs receive~ if it's about to ~openssl~-decrypt, or after
~zfs receive~ but before verification if it's about to unlock a ZFS key.
Either way, ~restore-test~'s usual cleanup (destroying the test dataset,
deleting the downloaded archive) still runs regardless.

Set ~ZFS_ENCRYPTION_PASSPHRASE~ (env var or Infisical, same precedence as
every other secret here) to the passphrase for ~:dataset~. It's piped to
~zfs load-key~'s stdin — never passed as a command-line argument or
written to a file, so it never appears in a process listing, mirroring
how ~BACKUP_ENCRYPTION_KEY~ is kept out of ~openssl~'s argv.

This is only ever consulted by ~restore-test~, and only for a dataset
that turns out to be ZFS-encrypted with verification actually running
(i.e. not ~--skip-verify~/Mode 3). Unlike ~PGCONNSTRING~, a missing or
wrong passphrase in that situation *aborts restore-test loudly* — the
whole point of restore-test is verifying a real restore actually works,
so silently skipping verification because the key couldn't be loaded
would defeat that. If your dataset isn't ZFS-encrypted, this secret is
never touched and can be omitted entirely.

**** Optional: Infisical for database and B2 credentials
:PROPERTIES:
:CUSTOM_ID: optional-infisical
:END:
~PGCONNSTRING~ and B2 credentials can instead be resolved from
[[https://infisical.com][Infisical]] at startup. This is opt-in and purely additive — an env var
present at runtime always wins over Infisical for that credential.

Add to ~config.edn~:

#+begin_example
{...
 :secret-store :infisical
 :infisical    {:project-id  "<infisical-project-id>"
                :environment "prod"        ; optional, default "dev"
                :secret-path "/"           ; optional, default "/"
                :site-url    "https://app.infisical.com"} ; optional, self-hosted only
 }
#+end_example

Infisical's own client credentials (~INFISICAL_CLIENT_ID~ /
~INFISICAL_CLIENT_SECRET~, or ~/etc/infisical/client_id~ /
~/etc/infisical/client_secret~) are resolved by
[[https://clojars.org/io.github.timotheosh/clj-infisical][clj-infisical]] itself and are never read from ~config.edn~.

Store these secrets in the Infisical project when using this mode:
~PGCONNSTRING~, ~B2_KEY_ID~, ~B2_APPLICATION_KEY~, and (only if
~:dataset~ is ZFS-encrypted) ~ZFS_ENCRYPTION_PASSPHRASE~. A missing or
failed ~PGCONNSTRING~ fetch just disables database persistence (logged,
never fatal — the database is always optional). A missing or failed B2
fetch *does* abort the run, since the backup can't reach the remote
without it. ~ZFS_ENCRYPTION_PASSPHRASE~ sits in between: it's silently
unused for non-encrypted datasets, but see [[#zfs-encryption-passphrase][ZFS encryption passphrase]]
above for when it *does* abort — loudly — for encrypted ones.

*** Database setup (optional)
:PROPERTIES:
:CUSTOM_ID: database-setup
:END:
Skip this entirely if you don't set ~PGCONNSTRING~ — manifest persistence
is a convenience index only, and the backup/restore pipeline is fully
functional without a database.

If you do want it, create one table. This exact DDL works unmodified on
either PostgreSQL (13+) or CockroachDB — both are driven through the same
~org.postgresql~ JDBC driver and both support ~UUID~/~JSONB~/~TIMESTAMPTZ~
and a built-in ~gen_random_uuid()~ natively:

#+begin_example
CREATE TABLE backup_manifests (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  snapshot   TEXT NOT NULL,
  manifest   JSONB NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
#+end_example

Run it with whichever client matches your database:

#+begin_example
$ psql "$PGCONNSTRING" -c "CREATE TABLE backup_manifests ( ... );"       # PostgreSQL
$ cockroach sql --url "$PGCONNSTRING" -e "CREATE TABLE backup_manifests ( ... );"  # CockroachDB
#+end_example

(On PostgreSQL older than 13, ~gen_random_uuid()~ isn't built in yet — run
~CREATE EXTENSION IF NOT EXISTS pgcrypto;~ first, or switch ~id~ to
~SERIAL PRIMARY KEY~ instead. CockroachDB has it natively at any version;
note that CockroachDB additionally warns that sequential IDs like
~SERIAL~ cause write hotspotting on a distributed cluster, so
~gen_random_uuid()~ is the recommended default there regardless.)

The application never creates or migrates this table itself, and only
ever touches the ~snapshot~, ~manifest~, and ~created_at~ columns — ~id~
exists purely to satisfy ~PRIMARY KEY~.

** Usage
:PROPERTIES:
:CUSTOM_ID: usage
:END:
#+begin_example
$ java -jar strategic-backup.jar backup
$ java -jar strategic-backup.jar restore-test [--skip-verify]
$ java -jar strategic-backup.jar --db-test
$ java -jar strategic-backup.jar --b2-test
#+end_example

- ~backup~ :: runs the full backup pipeline described above.
- ~restore-test~ :: downloads the latest backup, decrypts/decompresses it,
  ~zfs receive~s it into ~:test-dataset~, verifies every file's checksum
  against the manifest, then always destroys the test dataset and deletes
  the downloaded archive — pass or fail. Falls back gracefully: manifest
  from PostgreSQL/CockroachDB, else the newest local EDN manifest, else
  (or with ~--skip-verify~) restores the latest archive with no
  verification at all, clearly logged as skipped.
- ~--db-test~ :: resolves ~PGCONNSTRING~ (env var or Infisical, whichever
  ~config.edn~ is set up for) exactly as a real ~backup~/~restore-test~
  run would, then attempts a connection and a trivial query. Logs and
  exits ~0~/~1~ — nothing else runs. Useful as a pre-deploy or cron
  pre-flight check, or just to sanity-check a connection string without
  reaching for ~psql~/~cockroach sql~ separately.
- ~--b2-test~ :: same idea for B2 — resolves rclone credentials (env var
  ~RCLONE_CONFIG~ file, or Infisical's ~B2_KEY_ID~/~B2_APPLICATION_KEY~)
  and runs a lightweight ~rclone lsf~ against the configured bucket/prefix
  to confirm auth, bucket access, and network reachability, without
  uploading, downloading, or deleting anything. Logs and exits ~0~/~1~.

Exit code is ~0~ on success, non-zero on any failure — pipe stage, config
error, or verification failure — so a scheduler can detect and alert on it.
This applies to ~--db-test~/~--b2-test~ too, so they're safe to drop into
a deploy script or pre-flight cron check: ~strategic-backup --db-test &&
strategic-backup --b2-test && echo "ready"~.

** Scheduling with cron
:PROPERTIES:
:CUSTOM_ID: scheduling-with-cron
:END:
strategic-backup is a one-shot command, not a daemon, so it's driven by
the scheduler running it — cron or SMF. cron's environment is minimal, so
don't rely on your login shell's env being visible to it: use a small
wrapper script that sources a locked-down env file before invoking the jar.

*** 1. Env file
:PROPERTIES:
:CUSTOM_ID: env-file
:END:
~/etc/strategic-backup/env~, owned by the service account, mode 600:

#+begin_example
BACKUP_ENCRYPTION_KEY=<your key>
RCLONE_CONFIG=/etc/strategic-backup/rclone.conf
PGCONNSTRING=postgres://user:pass@localhost:26257/backups
STRATEGIC_BACKUP_CONFIG=/etc/strategic-backup/config.edn
#+end_example

(Omit ~RCLONE_CONFIG~/~PGCONNSTRING~ here if using Infisical mode instead —
then set ~INFISICAL_CLIENT_ID~/~INFISICAL_CLIENT_SECRET~ instead.)

#+begin_example
$ chmod 600 /etc/strategic-backup/env
$ chown backup-svc:backup-svc /etc/strategic-backup/env
#+end_example

*** 2. Wrapper script
:PROPERTIES:
:CUSTOM_ID: wrapper-script
:END:
~/usr/local/bin/strategic-backup-run~, mode 755:

#+begin_example
#!/bin/sh
set -a
. /etc/strategic-backup/env
set +a
exec /usr/bin/java -jar /opt/strategic-backup/strategic-backup.jar "$@"
#+end_example

*** 3. Crontab
:PROPERTIES:
:CUSTOM_ID: crontab
:END:
As the ~backup-svc~ user (~crontab -e~), nightly backup at 02:00 and a
weekly restore test Sunday at 03:00:

#+begin_example
0 2 * * *  /usr/local/bin/strategic-backup-run backup        >> /var/log/strategic-backup/backup.log 2>&1
0 3 * * 0  /usr/local/bin/strategic-backup-run restore-test   >> /var/log/strategic-backup/restore-test.log 2>&1
#+end_example

Make sure ~/var/log/strategic-backup~ exists and is writable by that user,
and that a real logrotate/newsyslog-equivalent is watching those files —
neither cron nor the jar rotates them.

*** Alternative: SMF
:PROPERTIES:
:CUSTOM_ID: alternative-smf
:END:
If you'd rather manage this as an SMF service than a crontab entry, the
same env vars can be set on the service instance directly instead of the
env-file/wrapper-script approach above:

#+begin_example
$ svccfg -s svc:/site/strategic-backup:default setenv BACKUP_ENCRYPTION_KEY '...'
$ svccfg -s svc:/site/strategic-backup:default setenv RCLONE_CONFIG '/etc/strategic-backup/rclone.conf'
#+end_example

illumos SMF has no built-in periodic/timer primitive equivalent to
systemd timers, so a transient SMF service still needs something
(typically cron) to trigger it on a schedule — SMF alone doesn't replace
cron's role here, it only replaces the env-file/wrapper-script for secret
injection.

** Future work
:PROPERTIES:
:CUSTOM_ID: future-work
:END:
- *TODO: drop the ~rclone~ dependency in favor of the native Backblaze B2
  API.* Every remote operation (~upload/rclone-copy!~, ~list-remote~,
  ~download-archive!~, ~delete-remote!~, ~test-connection!~) currently
  shells out to ~rclone~. B2's own HTTP API would remove an external
  binary dependency, give direct access to B2-specific features (e.g.
  lifecycle rules, large-file multipart uploads) that ~rclone~ only
  exposes indirectly if at all, and let ~:secrets :b2-rclone-env~ become
  real HTTP client credentials instead of environment variables shaped to
  match one particular tool's config format. Not a current requirement —
  ~rclone~ works and is well-tested here — but worth revisiting if
  ~rclone~ becomes a maintenance burden or a specific B2 API feature is
  needed.
